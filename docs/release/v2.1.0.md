# cli-forge v2.1.0 — Testable Output

**What a program prints can be tested now, without spawning it.** This release
also finishes the argument model 2.0 started — groups, negatable flags,
comma-separated lists — and adds plugins the way cargo has them and headings for
long help pages. Strictly additive: no 2.0 program needs editing to upgrade.

## What is cli-forge?

A unified command-line framework: argument parsing and styled output through one
API, with commands that register at runtime. It targets the lightness of argh with
the reach of clap, and — unlike either — keeps output styling in the *same* system
as parsing, so the sibling crates in the cli collection (`cli-table`,
`cli-progress`, gradients, layouts, shell) all build on one output layer.

## What's new in 2.1.0

### Output capture

Testing what a CLI prints normally means spawning the binary and reading its
pipes, which is slow, awkward to arrange, and blind to anything a library printed
on the program's behalf. `capture` redirects this crate's output into a buffer for
the duration of a closure instead:

```rust
use cli_forge::{capture, ok, out, warn, App, Command, Stream};

let mut app = App::new("forge");
app.register(Command::new("build").run(|_| {
    out("building...");
    warn("this build is not optimised");
    ok("compiled 3 targets");
}));

let (outcome, log) = capture(|| app.try_run_from(["build"]));

assert!(outcome.unwrap().is_ok());
assert_eq!(log.lines(Stream::Stdout), ["building...", "✓ compiled 3 targets"]);
assert!(log.err().contains("not optimised"));
```

That last assertion is the one worth having: the warning went to standard error
and the success did not. That's the stream discipline a theme is responsible for,
and before this there was no way to observe it from a test.

`Captured` gives `out()`, `err()`, `combined()` (both streams in the order lines
were written), `lines(stream)` (without trailing newlines, which makes a failing
assertion much easier to read), and `is_empty()`. It's per-thread, so capturing
tests run in parallel with printing ones; nesting works; and a panic inside the
closure can't leave the thread redirected.

It sees what goes through this crate — `out`, `err`, `write_to`, the themed
printers, and the reports `App::run` prints. Not `println!`, and not a child
process. `try_run_from` hands failures back rather than printing them, so a capture
around it sees handler output and nothing else.

### Argument groups

`conflicts_with` and `requires` describe pairs. Some rules are about a set:

```rust
Command::new("dump")
    .args([Arg::flag("json"), Arg::flag("yaml"), Arg::flag("toml")])
    .group(ArgGroup::new("format").args(["json", "yaml", "toml"]).required(true))
```

```text
$ export dump
error: one of --json, --yaml, --toml is required

USAGE: export dump [options] <--json|--yaml|--toml>
```

At most one by default; `required` makes it exactly one; `required` + `multiple`
is at least one. `m.group("format")` tells you which member was chosen, so
dispatching on it is a single `match`. A required group shows up in the usage
line, so users see the choice before they get it wrong.

A default answers a required group but never counts against the at-most-one rule —
otherwise a group whose members have defaults could never be satisfied.

### Negatable flags

```rust
Arg::flag("cache").negatable(true)    // --cache and --no-cache
```

The last spelling wins, so a shell alias can set `--no-cache` and the user can
still type `--cache`. `flag()` answers `false` for both "off" and "never
mentioned"; the new `explicit_flag()` keeps them apart (`Some(true)`,
`Some(false)`, `None`), which is what you need when a config file has its own
opinion. An explicit off never takes part in a conflict and never satisfies a
`requires`. Help shows `--[no-]cache`.

### Lists in one value

```rust
Arg::option("features").value_delimiter(',')    // --features serde,tokio
```

Each piece is validated on its own, so a typo in one gets its own "did you mean".
Empty pieces are kept rather than silently dropped, and defaults and environment
values split the same way.

### Plugins: external subcommands

```rust
App::new("forge").external(|ext| {
    // `forge watch src` runs `forge-watch src`
    std::process::Command::new(format!("forge-{}", ext.name()))
        .args(ext.args())
        .status()
        .map(|_| ())
})
```

This is how `cargo watch` works — a separate `cargo-watch` program that cargo finds
at run time. The hook gets the name, the untouched arguments after it, the
app-level arguments parsed before it (so a plugin inherits `-vv`), and the nearest
registered command for falling back to "did you mean". Registered commands and
flags are never handed off, and `try_parse_from` still has no side effects.

### Help headings

`Command::category("Release")` and `Arg::category("Network")` put an item under
its own heading instead of one long `COMMANDS:` or `OPTIONS:` list. Sections come
in the order their first item appears, and they share one column width, so the
descriptions stay in a single straight column down the page.

## Changed

**Relationship errors say what clashed.** The old wording described less than the
facts already in hand, and one of them was misleading:

| Before | After |
|---|---|
| `'--json' cannot be used with the arguments it conflicts with` | `'--json' and '--yaml' cannot be used together` |
| `the required argument 'format' was not provided` | `one of --json, --yaml, --toml is required` |
| `'sign' requires another argument that was not provided` | `'--sign' requires '--key'` |

`format` is a group's name, not something anyone can type. `kind()` and
`subject()` are unchanged, so code matching on them keeps working — error wording
was never part of the stability promise.

## Fixed

**Global arguments were deep-copied on every command level.** 2.0 cloned every
argument marked `global` at the top of each recursive parse, so a three-level
invocation paid for three full copies of each one. It now borrows, and the set is
built once. Two smaller allocations went with it: every flag formatted its own
display name up front, just in case a validation error needed it, and `-vvv`
allocated the argument name once per `v`.

## Breaking changes

**None.** Every addition is new API, and nothing existing changed behaviour.
Upgrading from 2.0 is a version bump.

## Performance

Counted heap allocations — deterministic, unlike wall-clock time — for an app with
three global arguments and a three-level command:

| | 2.0.0 | 2.1.0 | |
|---|---:|---:|---|
| allocations per parse | 132 | 96 | −27% |

I'm deliberately not quoting a parse-time improvement. Alternating runs of both
versions on the same machine moved by about ±15% each, which is more than any
difference between them. The benchmark app has no global arguments, so it never
exercised the copy that was removed, and the new negation and group checks add a
few lookups of their own. The saving is real; it shows up as allocations.

| Operation | Time |
|-----------|-----:|
| `out` plain write (`&str`) | ~9.5 ns |
| `out`, through a capture | ~25–40 ns |
| a themed line, through a capture | ~160–210 ns |
| parse a simple invocation | ~0.7–1.0 µs |
| parse a rich invocation | ~2.1–2.5 µs |

Criterion means on Windows x86_64, Rust stable. A range is how far the same code
moved between runs. With no capture active, the output path pays one relaxed
atomic load over 2.0 and is otherwise unchanged; the plain path stays
allocation-free, which `tests/allocation.rs` checks by measurement.

## The SemVer promise

Unchanged from 2.0: no breaking change before 3.0, additions are minor, fixes and
optimisation are patch, and the 1.85 MSRV rises only in a minor. `ArgGroup`
accessors, `External`, and the new `Matches` readers are covered from this release
on. `External` is `#[non_exhaustive]`, so it can carry more context later without
a major bump.

The full promise lives in the
[Stability](https://github.com/jamesgober/cli-forge/blob/main/docs/API.md#stability)
section of `docs/API.md`.

## Verification

Run on Windows x86_64, Rust stable 1.95.x, with the CI matrix covering
Linux/macOS/Windows × stable/1.85 and all eight selectable feature combinations.

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --no-default-features --all-targets -- -D warnings
cargo test --all-features
cargo test --no-default-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
RUSTUP_TOOLCHAIN=1.85 cargo test --all-features
cargo bench --bench bench
cargo deny check
cargo audit
python dev/check-doc-links.py
python dev/check-api-docs.py docs/API.md
```

All green. Counts at this tag (`--all-features`):

- 310 unit tests, including 23 property tests.
- 20 integration tests — the allocation proof, non-`main` registration, the
  README's own examples, and a new environment-fallback suite. `Arg::env` had
  only ever been tested with its variable unset until now.
- 403 documentation tests, including every code block in the guides.

179 of those pass on the bare `no_std` build. `docs/API.md` covers all 270 public
items.

## Installation

```toml
[dependencies]
cli-forge = "2.1"

# With the auth seam:
cli-forge = { version = "2.1", features = ["auth"] }

# No dependencies at all:
cli-forge = { version = "2.1", default-features = false, features = ["std", "color"] }
```

MSRV: Rust 1.85.
